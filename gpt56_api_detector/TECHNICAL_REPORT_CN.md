# GPT-5.6 加密推理状态兼容性检测：技术报告

## 1. 检测目标

本工具解决的是 API 能力审计问题：给定一个可信 GPT-5.6 Responses API 和一个待测 API，判断待测端点是否能够消费可信端点产生的 `reasoning.encrypted_content`，并从中恢复客户端可验证的隐藏结果。

检测对象是“加密推理状态兼容性”，不是模型权重身份。黑盒客户端只能观察请求和响应，无法判断候选服务是在本地运行兼容模型、转发给其他后端，还是使用保持协议兼容的另一实现。因此，通过测试所支持的最强结论是：候选端点表现出与可信 GPT-5.6 来源相容的状态消费能力。

该工具同样不读取明文 chain of thought。`encrypted_content` 始终作为不透明字符串处理；实验只验证它是否携带足以恢复特定结果的信息。

## 2. 挑战构造

每个有效 trial 由客户端通过 `secrets` 模块生成新的 10 位随机输入。客户端在本地计算唯一的预期答案 B，变换函数在三类任务之间轮换：反转十位数字、把前三位移动到末尾、逐位计算 `9-d`。这些变换保留十位定长表示，因此前导零也参与精确匹配。

可信模型收到原输入和计算要求，被要求在隐藏推理中得到并保留 B，而可见正文只能输出 `READY`。请求同时要求 Responses API 返回 `reasoning.encrypted_content`。可信响应必须包含非空 reasoning 密文；随后可信模型还要仅依靠该状态精确恢复 B。若生产者自身不能恢复，说明该状态没有可靠承载目标信息，本次尝试被拒绝，不计入有效样本。

候选请求不包含原始随机输入、变换后的 B 或可信源提示词。它只接收可信响应的 output item 和一条要求恢复隐藏结果的新消息。脚本在发送前递归扫描候选 payload，若发现原始输入或 B 出现在请求明文中，直接把整个运行判为 `invalid`。

## 3. 因果对照

单独观察候选端点返回正确答案不足以证明信息来自密文。答案可能来自可见文本、response ID、固定偏好、缓存污染或实现泄漏。为此，每个状态都生成四个实验条件。

完整状态保留 reasoning item 和可见消息，是阳性条件。删除 ID 条件递归移除所有 output item ID，但保留 `encrypted_content`；若仍能恢复，可排除必须按 ID 向服务端查询原响应的解释。message-only 条件只保留可见 `READY` 消息；它应无法恢复随机 B。密文篡改条件修改密文中的一个字符，同时保持其他结构不变；它应因完整性校验或解密失败而无法恢复。

可靠的兼容模式因此不是一次命中，而是成组出现：完整状态命中、删除 ID 后仍命中、仅正文不命中、篡改密文不命中。两种阳性条件证明可用性，两种阴性条件约束信息来源。若阴性条件返回正确答案，脚本输出 `suspicious`，因为这更符合请求泄漏、端点耦合、缓存串扰或测试实现错误，而不是干净的密文回放。

## 4. 决策规则与统计意义

默认运行要求收集 12 个有效挑战。阳性门槛为 `max(min_matches, ceil(min_match_rate * N))`，默认 `min_matches=4`、`min_match_rate=0.5`。完整状态与删除 ID 状态必须分别达到门槛；message-only 和篡改密文必须零精确命中；请求泄漏计数必须为零。

在理想化盲猜零假设下，均匀十位答案单次精确猜中的概率至多为 `10^-10`。脚本计算观察到至少 k 次命中的二项分布上尾概率。多次独立精确恢复可以有力排除偶然猜测，但这个数值不是对抗性安全证明：能访问兼容解码器或能把探针流量代理给兼容模型的候选服务，本来就应当通过。

门槛没有设成 100%，因为状态生产、网关路由、超时和消费过程可能存在非确定性。对于高价值审计，建议使用 20 个有效 trial，并提高到 `--min-match-rate 0.75 --min-matches 15`，在不同时间窗口重复运行。一次 `not_compatible_in_this_probe` 只能说明当前配置和时间窗口未观察到兼容性，不能证明模型永远无法消费该状态。

## 5. 为什么不能区分 Sol、Terra、Luna

加密状态检测测量的是兼容域，而非唯一模型标签。如果 Sol 产生的状态可被 Terra 或 Luna 消费，成功回放只说明候选落在同一兼容域。状态格式、密钥域或后端服务可能在多个变体之间共享，这会使跨变体回放成为预期行为。

延迟、文风、token 使用量和基准题表现也不能可靠补足身份判断。它们会受到系统提示词、采样参数、量化、路由、缓存、负载和代理层影响，并可被有意模拟。因此工具明确只输出 GPT-5.6 encrypted-state compatibility，不输出 Sol/Terra/Luna 分类结果。

## 6. 威胁模型与不可伪造性边界

本协议可以抵抗意外盲猜、可见正文携带答案、简单 ID 查询和单字符密文损坏等替代解释。它还通过每次刷新随机挑战，降低静态答案表和普通响应缓存命中的可能性。

它不能抵抗拥有兼容后端的主动候选服务。候选可以把整个请求透明转发给真正的 GPT-5.6 兼容端点，或者识别探针流量后切换路由。只要最终行为正确，黑盒客户端无法区分代理与本地执行。要实现不可伪造的物理模型身份认证，需要服务端签名、可信执行环境远程证明、模型权重度量或由平台提供的硬件级 attestation；这些能力不属于普通 Responses API。

可信端点也是信任边界的一部分。若可信源不是预期模型、泄漏挑战或与候选共享隐藏状态，结论会失效。审计时应控制可信端点、保护日志、固定模型配置，并尽可能让两个端点由不同管理域运行。

## 7. 报告与数据最小化

输出报告记录模型标签、端点 URL、条件命中情况、HTTP 状态、延迟、答案长度和 SHA-256、密文长度和 SHA-256、被拒绝的可信状态原因，以及统计摘要。报告不保存原始随机输入、预期答案、候选原始输出、原始密文或 API key。

哈希用于关联和审计单次运行，不会把十位答案变成高熵秘密。由于十位空间可以被穷举，报告中的答案哈希不应被视为密码学承诺或长期保密机制；它只是避免在常规日志中直接展示答案。原始 API 流量仍可能被本地代理、服务商或调试日志记录，运行环境应按敏感测试处理。

## 8. 正确表述

推荐报告格式：

> 候选端点在 N 个随机、客户端可验证的挑战中，恢复了 X 个完整加密状态和 Y 个删除 item ID 后的状态；message-only 与密文篡改对照均为零命中。这表明候选 API 兼容可信 GPT-5.6 来源产生的加密 reasoning state。该结果不构成模型权重或托管身份的密码学证明，也不能区分 GPT-5.6 Sol、Terra 和 Luna。

不应使用“已证明服务器物理运行 GPT-5.6 Sol”“无法伪造”或“成功提取明文 CoT”等超出证据范围的表述。
